# Release Notes

Notable changes to go-pkicmp. Versions follow the `vMAJOR.MINOR.PATCH` tags published in this repository.

## v0.0.2 - TBD

Hardening release for response authentication and shared-secret protection, together with client fixes for enrolling against CAs that issue from an intermediate, route on the recipient name or stop sending certificates partway through an operation.

A client could previously be talked into accepting a forged issuance response by an attacker holding nothing more than a certificate that chains to any configured trust anchor. Two independent gaps allowed it and both are now closed: a signature is accepted only from the sender the message names, and the returned certificate must certify the key that was actually requested. A third control, requiring one protection mechanism throughout an operation, is available through the new **`WithResponseProtection`** client option rather than applied automatically, because CAs legitimately answer a shared-secret request with a signature.

Shared-secret protection is hardened separately. PBKDF2 parameters taken from a received message are bounded before they reach key derivation, which closes a remote crash reachable before the message is authenticated, and PBMAC1 messages that leave out the optional PBKDF2 fields now interoperate instead of being rejected as malformed.

Five client defects that prevented reliable enrollment are fixed: recipient names built in Go now reach the wire, certificates issued by intermediates validate against the configured root, the final `pkiConf` verifies when the CA sends certificates only once, authenticated CMP failures remain readable on HTTP error responses and delayed issuance accepts the nonce of the original request.

A rejection that a client cannot verify is no longer lost. A CA signs its error messages however the request was protected, so a client enrolling with a shared secret and no trust anchors could not read one; the claimed status is now reported as an explicitly unauthenticated result. Nothing about enrollment changes for such a client, and a device that has no anchor yet remains a supported configuration. Polling is bounded in the same release: each interval a server asks for is clamped into a configurable range, so a peer can no longer park an enrollment indefinitely or drive it into a tight request loop.

On the server side, the whole enrollment matrix of the OpenSSL and Nokia CMP clients now completes, which previously it did not. Several RFC 9483 rules govern how a peer must build a message rather than how the server authenticates it, and these clients break them while remaining secure and specification-defensible. Those checks are now gathered behind the new **`WithStrictProfileValidation`** option, off by default, so a deployment chooses between interoperating with what is in the field and enforcing the profile strictly.

### Security fixes

* **The accepted protection mechanism can now be pinned for a whole operation.** Verification dispatches on the algorithm named in the received message, so a caller holding a shared secret that also configured trust anchors accepts a signature-protected response from any certificate chaining to one of those anchors. RFC 9483 §3.1 asks for the same kind of protection throughout a PKI management operation, and RFC 9810 §5.2.3 reserves the failInfo bit `wrongIntegrity` for a message that arrives "password based instead of signature or vice versa". Clients can now require a mechanism with **`client.WithResponseProtection`** and direct users of `pkicmp` with the new **`VerifyOptions.RequiredProtection`** field. Both default to `ProtectionAny`, which accepts either mechanism, because CAs configured to sign every response while authenticating clients by shared secret are common and remain interoperable, and because RFC 9810 §5.3.21 requires an error message to be signed however the request was protected. Pinning is a defense in depth measure: a response is bound to its operation by the transaction ID and nonces, a signature must chain to a configured anchor and name its own protection certificate, and an issued certificate must certify the requested key.
* **Signature-protected messages must come from the sender they name.** Signature verification accepted the first certificate in `extraCerts` that chained to the trust pool and produced a valid signature, without ever comparing the header sender to the certificate subject. Chaining to a trust anchor only proves a certificate is trusted, so for an enterprise or public CA any certificate under that anchor was accepted for any claimed identity. The sender is now bound to the subject of the certificate that produced the signature, as RFC 9483 §3.5 requires, and a mismatch is reported as `ReasonSenderMismatch`. A NULL DN sender, which RFC 4210 §5.1.1 requires when the sender does not know its own name, carries no name to compare and is still accepted on the trust chain alone.
* **The issued certificate must certify the requested public key.** The client returned whatever certificate the response carried, checking only that it chained to a trusted CA. A compromised or buggy CA could therefore hand back a certificate for a key the client does not hold, which the client would store and only discover later as an unexplained TLS failure. The public key is now compared against the request before the certificate is returned. The **subject is deliberately not compared**, because a CA may legitimately return `grantedWithMods` after changing requested fields such as the subject.
* **PBKDF2 parameters from a received message are bounded before key derivation.** The PBKDF2 `keyLength` in a received message was used exactly as sent, before the message was authenticated. A negative or very large value crashed the process inside key derivation, so any peer able to reach a CMP endpoint could take it down without knowing the shared secret. A very small value was dangerous in the other direction: a one-byte key leaves 256 possible MAC keys, few enough to search and forge protection with. The accepted range is now **16 bytes through the MAC block size**, and anything outside it is rejected with a `ParseError` before any derivation runs. The floor is an absolute key strength requirement rather than the MAC digest size, so the widespread practice of deriving 32 bytes for every MAC keeps working with HMAC-SHA-384 and HMAC-SHA-512. The same bounds apply when a server protects a response with `WithProtectionAlgorithm`, which echoes the parameters from the request.
* **Unsupported hash algorithms in PBMAC1 parameters are rejected instead of crashing.** A message naming a hash that is not linked into the binary previously reached key derivation and panicked. It now returns a `VerificationError` with reason `ReasonUnsupportedAlgorithm`.
* **An expired protection certificate no longer authenticates.** When a server resolved the signer through `WithCertificateLookup`, only the signature was checked, so a certificate left in the CA's own store kept authenticating its holder indefinitely after it expired. The validity period is now checked on that path too and a violation is reported as `ReasonCertificateExpired`.
* **The `digitalSignature` key usage can now be required on protection certificates.** RFC 9483 §3.5 requires the `digitalSignature` bit whenever the CMP protection certificate carries a `keyUsage` extension, and it was never checked. Enforcement is available through the new **`VerifyOptions.RequireDigitalSignatureKeyUsage`** field, reported as `ReasonKeyUsageNotPermitted`, and is off by default because deployed CAs protect CMP with a CA certificate that sets only `keyCertSign` and `cRLSign`.
* **Polling intervals are bounded.** The `checkAfter` value of a `pollRep` is an integer chosen by the peer and was used exactly as sent. A value past what a duration can hold wrapped to a negative interval, so the client polled again immediately and turned a delayed issuance into a tight request loop against the CA, while a merely large value parked the caller for years with nothing but a context deadline, which the caller may not have set, to stop it. Each wait is now clamped to a range defaulting to **1 second through 60 seconds**, configurable with the new **`client.WithCheckAfterLimits`**. Together with the existing 60-attempt limit this bounds an unattended enrollment to about an hour. Raise the ceiling for a CA that issues only after a slow out-of-band approval, and set a context deadline to match.
* **A data race in server transaction cleanup is fixed.** Completing a transaction updated its record in place while a concurrently running `CleanupExpired` was reading the same record, so the expiry timestamp could be read torn. The consequence was either a live transaction deleted early or an entry that never expired and permanently consumed a transaction slot. Completion now publishes a new record like every other state change. The recommended deployment, a background goroutine calling `CleanupExpired`, is exactly the one that triggered this.

### Bug fixes

* **The recipient name now reaches the wire.** `client.WithRecipient` was silently ignored unless the name had been decoded from a certificate, because the client decided whether a recipient had been configured by looking at `pkix.Name.Names`, a field Go populates only when parsing. A name built in Go left it empty, so the request went out with no recipient at all and CAs that route on that field refused it, typically with `wrongAuthority`. Any name carrying at least one attribute is now sent.
* **Certificates issued by an intermediate CA now validate against the root.** The issued certificate was verified against the configured trust anchors alone, with no intermediates, so a CA that issues from a subordinate CA and returns that subordinate in `extraCerts`, which RFC 9810 §5.1 provides for exactly this purpose, failed with `certificate signed by unknown authority`. Working around it meant trusting the intermediate as an anchor. The certificates from the response are now used to build the path, so configuring only the root works.
* **The final `pkiConf` now verifies when the CA sends its certificates only once.** A CA may include `extraCerts` on its first response and omit them afterwards, which RFC 9810 §5.1 permits. The client resolved a signer only from the message in hand, so the closing `pkiConf` failed verification and the enrollment was reported as failed even though the certificate had been issued and confirmed. The protection certificate authenticated earlier in the operation is now retained and offered for later messages, which must still satisfy the same chain, sender and signature checks against it. Callers using `pkicmp` directly can do the same with the new **`VerifyResult.ProtectionCertificate`** field.
* **Authenticated CMP failures remain available on HTTP error responses.** RFC 9811 Section 3.1 requires clients to handle a CMP `PKIMessage` carried by an HTTP 2xx, 4xx or 5xx response. The client previously returned immediately for every status except 200 and discarded protected failure details such as `transactionIdInUse`. It now parses and verifies advertised CMP content before returning the error. Helpers such as `pkicmp.HasFailure` can inspect the authenticated failure bits while the error still reports the HTTP status. Responses without usable CMP content continue to return the HTTP error.
* **A rejection the client cannot authenticate is reported instead of discarded.** RFC 4210 §5.3.21 and RFC 9810 §5.3.21 both require a CA to sign an error message however the request was protected, so a client enrolling with a shared secret and no trust anchors cannot verify one. The enrollment failed with nothing but a verification error, hiding the reason the CA gave, and `transactionIdInUse` is exactly the reason a caller needs in order to decide whether to retry. The claimed status now comes back as the new **`client.UnverifiedStatusError`**, which carries the status, the failure bits and the server's text, and the failure names the missing configuration. **Nothing in that error is authenticated**: any peer able to answer chooses those values, the server's free text is deliberately left out of the error message, and `pkicmp.HasFailure` continues to report only verified failure bits. Enrollment itself is unchanged, and a device holding only an initial authentication key still enrolls with no anchors at all. Set **`client.WithTrustedCAs`** wherever an anchor is already available, so that a rejection is verified rather than merely logged.
* **CMP media types follow HTTP parsing rules.** Both the client and server previously compared `Content-Type` to the exact string `application/pkixcmp`, which rejected valid case variations and media type parameters. They now parse the value according to HTTP media type syntax, accept `Application/PKIXCMP` and values such as `application/pkixcmp; charset=binary`, then continue to reject malformed or unrelated media types.
* **Delayed-delivery responses accept the nonce of the original request.** During polling the final response may identify the request whose processing was delayed instead of the latest `pollReq`, as RFC 9483 Section 4.4 requires. The client now retains that original `senderNonce` and accepts either valid reference for the final response. A `pollRep` remains bound only to its matching `pollReq`.
* **PBMAC1 messages that omit the optional PBKDF2 fields now verify.** RFC 8018 A.5 marks `keyLength` as OPTIONAL and gives `prf` a DEFAULT of HMAC-SHA-1, and DER requires an encoder to leave out a field that holds its default. Both fields were nevertheless required when parsing, so a conforming peer that omitted either one was rejected with `invalid PBKDF2-params` and could not enroll at all. An absent `keyLength` now defaults to the MAC digest size and an absent `prf` now defaults to HMAC-SHA-1, as the specification requires. Servers echoing such a request back in a response handle the omitted fields the same way. The encoder follows the same rule and now leaves `prf` out when it holds the HMAC-SHA-1 default, which DER requires.
* **`confirmWaitTime` is sent as a `GeneralizedTime`.** RFC 9810 §5.1.1.2 defines the value as the instant by which the certificate confirmation is expected, and it was sent as an integer count of seconds instead. A conforming client rejected the whole response, so every server response that did not grant implicit confirm was unusable: OpenSSL failed the transaction outright. The value is now the deadline as a `GeneralizedTime`, and the new **`pkicmp.ParseConfirmWaitTime`** reads it.
* **CMP-specific extended key usages on a protection certificate are accepted.** Verification left the accepted extended key usages unset, which makes Go's `crypto/x509` silently demand `serverAuth`. A CA or RA certificate marked with the CMP usages that RFC 9810 §4.5 defines for exactly this role, `id-kp-cmcCA`, `id-kp-cmcRA` or `id-kp-cmKGA`, was therefore rejected with a misleading `signature verification failed`. Any extended key usage is now accepted for protection verification, matching how issued certificates were already validated.
* **Response `extraCerts` lead with the CMP protection certificate and no longer repeat one.** RFC 9483 §3.3 puts the protection certificate first, followed by its chain, and a certificate supplied through `WithExtraCerts` could both displace it and appear twice. Responses now start with the protection certificate and carry each certificate once.
* **Distinguished names keep attributes that Go cannot rebuild from typed fields.** Building a CMP name from a `pkix.Name` dropped every attribute without a dedicated Go field, notably `UID` and `domainComponent`, so a recipient copied from a CA certificate went out truncated. Such a CA name is common, for example an EJBCA `ManagementCA` whose subject carries a `UID`. The full name is now encoded. Use `NewDirectoryNameFromRawDER` when the original bytes must be preserved byte for byte.

### Server behavior

* **The strict RFC 9483 message construction rules are now opt in through `WithStrictProfileValidation`.** Four checks reject messages that authenticate correctly but are not built the way the profile prescribes: a MAC-protected message whose sender is not a `directoryName`, a signature-protected request with no `extraCerts`, one whose `extraCerts` are not the protection certificate followed by its complete chain, and a `certConf` reusing a `senderNonce`. Each is now off unless the option is set. They are receiver-side construction rules rather than authentication: the server identifies a client from `senderKID` or `WithCertificateLookup` and binds the transaction with the recipient nonce, so none of them affects who is allowed to enroll. Leaving them on by default made enrollment impossible for clients that are behaving reasonably. RFC 4210 §5.1.1 in fact *requires* the NULL-DN sender that RFC 9483 forbids, when the end entity does not yet know its own name, which is the normal bootstrap case. Turn the option on to run a conformance suite or where every client is known to follow the profile.

## v0.0.1 - 2026-05-27

Initial pre-release, providing a partial implementation of CMP as specified in RFC 9810, which obsoletes RFC 4210, profiled by RFC 9483 (Lightweight CMP Profile), with RFC 4211 (CRMF) and RFC 6712 (CMP over HTTP), split into three packages. Both protocol versions defined by RFC 9810 are supported, so the library interoperates with peers implementing the original RFC 4210 CMPv2 (`cmp2000`) as well as CMPv3 (`cmp2021`).

### Features

* **`pkicmp`** provides the core CMP and CRMF ASN.1 types, covering parsing, serialization, PVNO 2 and 3, and message protection using either a shared secret (PasswordBasedMac and PBMAC1) or X.509 signatures.
* **`client`** implements the IR, CR, KUR and P10CR enrollment flows, including polling for deferred issuance, response verification and certificate confirmation.
* **`server`** exposes a CMP endpoint as a standard `http.Handler` that authenticates clients, tracks transactions, supports asynchronous issuance and enforces policy through middleware, including the Lightweight CMP Profile.

Interoperability is exercised by integration tests: the client against EJBCA and OpenSSL, and the server against the Siemens CMP Test Suite.
